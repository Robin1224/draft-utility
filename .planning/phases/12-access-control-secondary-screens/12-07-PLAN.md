<objective>
Install the real security boundary: a throwing authorization guard inside the `lobby` stream init (ACC-03 / D-01), placed above the unconditional guest upsert, plus the matching room-privacy guards in `chatAll` and `chatSpectators` (D-20). Guests remain admitted whenever the room is public or the draft has started (ACC-04).

Purpose: SSR `gated` is trivially bypassable — a client can open the WebSocket directly and call `room/lobby` without ever fetching the page. This plan is the layer that cannot be bypassed. It is also the phase's highest-consequence code: the difference between throwing and returning a gated payload is the difference between a closed boundary and a full roster leak.
Output: one guard in `src/live/room.js`, two guards in `src/live/chat.js`, repaired fixtures and new tests in `src/live/room.spec.js` and `src/live/chat.spec.js`.
</objective>

(`server.d.ts:95-105`) with no per-event filtering. The gated-payload option is a data leak.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser (or any WebSocket client) → `src/live/room.js` `lobby` stream | THE authorization boundary for room data. A scripted client reaches it without ever fetching a page, so this is the only enforcement point that cannot be bypassed |
| browser (or any WebSocket client) → `src/live/chat.js` `chatAll` / `chatSpectators` | The second data surface of a private room. Previously unguarded for room privacy |
| stream init → topic membership | `ws.subscribe(topic)` has ALREADY happened when the init handler runs; only a throw rolls it back |
